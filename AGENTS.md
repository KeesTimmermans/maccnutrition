# Project rules

- Signup (OnboardingQuestionnaire) asks only essentials; the other questions live in the Today "Complete your profile" card, which reuses the same step components via `essentialsOnly` / `extrasOnly` props. Why: one source of question UI for both places.
- Profile sections save as partial `user_baselines` updates (`saveProfileSection`), never through `saveUserBaseline`, and recalculate targets only when a target-affecting field is included (`affectsTargets`). Why: `saveUserBaseline` overwrites the whole row.
- Food approach lives in `user_baselines.tracking_mode` ('calories' | 'habits'); read it through `normalizeTrackingMode` / `useTrackingMode` (wait for `loading`), and never recalculate targets when it changes. Why: unknown values must fall back to calorie tracking, and the setting changes what the app shows, not the targets.
- The mode is loaded once by `TrackingModeProvider` (App.tsx, inside HashRouter) and read with `useTrackingMode`; calorie/macro figures render only when `showNumbers(mode, loading)` is true, and hiding is display-only (analysis, saves and meal edits keep the full stored numbers). Why: switching must be instant everywhere, habits users must never see a flash of numbers, and switching back must lose nothing.
- Habits-mode bi-weekly check-ins never change targets: ProgressUpdateDialog persists `unchangedTargetsAdjustment` (zero delta) instead of `applyProgressAdjustment` and hides adjustment UI. Why: habits users have no visible targets, so nothing may silently shift them.
- BaselineSummary takes the questionnaire's `trackingMode` as a prop and prefers it over the shared mode. Why: it renders right after signup, before TrackingModeProvider has re-read the saved setting.
- Number-free counts for habits mode (meals per day, days logged, water-goal days) live in `src/lib/habitProgress.ts`; AI/coach text shown to habits users is filtered with `mentionsNutritionNumbers` / `coachParagraphs`. Why: one tested source for what habits users may see.
- Coach Mac habits mode is decided on the server: ai-coach and generate-weekly-habit read `user_baselines.tracking_mode` themselves (errors = calories). Habit prompt pieces live in `ai-coach/habitPrompt.ts` and are applied only when `isHabit`; the calorie prompt text stays untouched. Why: the client can't be trusted for the mode, and calorie users must keep identical behaviour.
- `supabase/functions/_shared/habitGuard.ts` is pure TS (no Deno imports) and checks/strips only prose outside ```json blocks; habits replies get one rewrite retry, then sentence stripping, never an empty reply. Why: meal cards keep their hidden numbers for one-tap logging, and vitest tests the same file.
- Today's checklist is one `daily_checklists` row per user per local date, created only by `generate-daily-checklist` (insert-ignore, then reselect) and never regenerated; the client only updates `completed` and appends check-in items (`ci-N`). Why: the list must stay stable for the day and survive reloads.
- Checklist item rules (validation, vague-title ban, fallback library, deterministic water + weekly habit items) live in `supabase/functions/_shared/checklistRules.ts` (pure TS, tested by vitest); auto-tick and progress logic lives in `src/lib/dailyChecklist.ts`. Why: server and tests share one source, and auto items tick from live day data instead of stored ticks.
- The weekly habit appears on the checklist but its tick is the `weekly_habits.completed_dates` entry; both cards stay in sync through `WEEKLY_HABIT_CHANGED_EVENT`. Why: one source of truth for the habit streak.
- Every checklist item and weekly habit has a category (nutrition | sleep | stress | hydration) and must never ask the user to exercise; the patterns, keyword classifier and category-mix rules live in `_shared/checklistRules.ts` and the client imports them from there. Saved lists with an uncategorised item are deleted and regenerated by the function. Why: one source for the no-workout rule on server, client and tests.
- The no-exercise rule in `_shared/checklistRules.ts`: exercise actions and train instructions are always rejected (title or why); training-timing words pass only next to an eating/drinking word (meal-time nouns don't count). Users with training days get exactly one "If you train today:" nutrition/hydration item via `applyTrainingNutritionRule`; `trainingOnly` fallbacks are never picked otherwise. Why: nutrition around training is wanted, asking users to train never is, and we don't know which days they train.
- Habits-mode weekly recap and the "What should I eat next?" card take all wording from fixed libraries (`src/lib/habitRecap.ts`, `src/lib/whatNext.ts`, keys equal the i18n keys) and make no AI calls; past checklist days are re-evaluated with `isItemDone` from that day's meals, water and check-in. Why: auto ticks aren't stored, and habits users must never see nutrition numbers.
- Scan & rate: the `product-score` function only fetches and cleans Open Food Facts data (no scoring); all scoring lives in pure `src/lib/foodScore.ts` with every weight as a named constant, and reasons/bands are i18n keys. Why: weights stay easy to tune and fully unit-tested, and the server stays a thin lookup.
- `product-score` must request `nutriments` without also listing `fruits-vegetables-nuts-estimate-from-ingredients_100g` in `fields`; read that value from inside nutriments. Why: Open Food Facts drops the rest of nutriments when that sub-field is requested on its own.
- New tools go in the `TOOLS` array in `src/pages/Tools.tsx` (one entry each, no placeholder cards). Why: the Tools tab is a list that grows one tool at a time.
- Scan & rate alternatives: `product-alternatives` only searches/cleans OFF records (`_shared/offProduct.ts`, `_shared/offCategories.ts`); picking lives in pure `src/lib/productAlternatives.ts`. If v2 search fails it falls back to search.openfoodfacts.org (Nutri-Score A/B, top hits re-read in full); a chosen store only adds/ranks results. Why: v2 search mostly 503s server-side and store tags are sparse.
